# 从 0 开始的新项目：文档治理初始化提示词

你是本项目的编码智能体（Codex、GLM5、Claude Code 或同类工具）。请先在当前项目根目录建立完整的“文档优先”开发治理体系，再开展任何业务编码。除非我明确指定其他语言，文档使用中文，必要技术术语可中英并列。

## 一、目标

建立可长期维护、可审计、可交接的项目文档体系。所有功能和模块都必须遵循：先写文档并明确验收标准，再依据文档开发；开发过程中持续记录；开发完成后回写实现、测试、发布和项目进度。

## 二、必须创建的文档层级

在项目根目录创建 `docs/`，至少包含：

- `docs/00-governance/`：文档原则、工作流、分类层级、命名版本、状态流转、模板。
- `docs/01-product/`：项目章程、路线图、需求与用户故事。
- `docs/02-architecture/`：架构总览、模块边界、数据模型、接口集成、安全与 ADR。
- `docs/03-development/`：开发约定和按工作项分组的 `features/`。
- `docs/04-project-tracking/`：全项目看板、里程碑、风险阻塞、变更记录。
- `docs/05-quality/`：测试策略、测试报告、质量门禁。
- `docs/06-operations/`：部署、运维手册、监控与故障复盘。
- `docs/07-reference/`：术语表、外部资料与约定索引。
- `docs/08-archive/`：废弃或历史文档，保留替代关系。

创建 `docs/README.md` 作为全局入口，解释每一层放什么、主事实源在哪里以及如何开始一个新工作项。

## 三、每个功能或模块的强制文档

每个功能建立独立目录：`docs/03-development/features/FEAT-xxxx-<kebab-case-slug>/`，并包含：

1. `00-feature-spec.md`：背景、目标、范围/非范围、用户故事、验收标准、依赖、风险、回滚思路。
2. `01-technical-design.md`：现状、方案、接口、数据结构、关键流程、安全、兼容与迁移、备选方案。
3. `02-implementation-plan.md`：可执行任务、顺序、负责人、文件/模块影响、验证方法。
4. `03-implementation-log.md`：按日期记录真实改动、关键命令、偏差、决策、阻塞和未完成项。
5. `04-test-report.md`：环境、用例、结果、失败、证据和未覆盖边界；静态检查不得冒充运行时或真实环境验收。
6. `05-release-and-handoff.md`：发布内容、配置/迁移、回滚、已知问题、运维和交接信息。

BUG、CHORE、SEC 等工作可使用相同六文档闭环和对应编号前缀。纯只读分析可不创建工作项目录，但一旦修改代码、配置、数据或发布状态，就必须建档。

## 四、状态与看板

创建 `docs/04-project-tracking/board.md`，至少包含 Backlog、Ready、In Progress、Review、Blocked、Done。每条记录必须包含：工作项 ID、标题、负责人、优先级、状态、依赖、目标日期、阻塞、文档链接、最近更新时间。

文档状态统一使用：`draft -> ready -> in_progress -> review -> done -> archived`；被阻塞时标记 `blocked` 并说明原因。看板是项目状态主事实源，工作项目录是详情主事实源，两者必须同步。

## 五、写入 AGENTS.md 的强制规则

在根目录 `AGENTS.md` 中以受管标记块增量写入规则，保留已有内容。规则必须覆盖：

- 无已完成规格和明确验收标准，不得开始编码。
- 开发前读取项目索引、看板、相关架构和工作项文档。
- 开发中同步维护实施日志，方案偏离时先更新设计。
- 完成前必须同步测试报告、发布/交接文档和看板。
- 文档新增、更新、归档触发条件。
- 分类、命名、编号、状态、链接和责任人规范。
- 完成定义 DoD：代码、测试、文档、看板、发布/回滚信息一致。
- PR/提交检查项必须包含文档影响和验证边界。
- 禁止虚构测试结果、线上状态、负责人、日期或需求。

## 六、新项目专属要求

- 创建项目章程和路线图模板，但不替我虚构业务需求、技术栈或发布日期。
- 将“文档治理初始化”记录为首个已完成工作项。
- 将“确认项目目标与首个业务功能”放入 Backlog。
- 对所有 `<待确认>` 字段集中列出下一步需要我确认的事项。

## 七、安全和验收

- 默认非破坏性：不覆盖已存在文件，不删除、不移动既有内容。
- 重复执行必须幂等；受管规则仅更新受管标记块。
- 完成后运行只读完整性检查。
- 最终报告必须分别列出：模式判断、已创建、已更新、已保留、待人工补充、检查结果。不要把空模板或静态检查描述成业务设计、功能完成或运行时验收。

请先完成文档体系和规则初始化，报告结果并等待/读取项目需求，然后才进入首个业务功能的文档阶段。
