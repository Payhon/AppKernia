# 什么是 AppKernia？

AppKernia 是一套面向真实 App 项目的开源开发基座：它把移动端、后台管理端和服务端放进同一套契约、权限、安全、国际化与工程流程里，让开发者可以从一个能运行的起点出发，而不是每次都重新拼装登录、用户、租户、文件、通知和管理后台。

它不是一个套上移动端外壳的 Admin 模板，也不是只提供 UI 的跨端组件库。AppKernia 想解决的是更长的一段路：从用户第一次打开 App，到运营人员在后台管理数据，再到 API、Worker 和 PostgreSQL 安全地完成业务。

<div className="ak-doc-callout">
  <strong>一句话理解</strong>Mobile 负责用户体验，Admin 负责运营工作流，Server
  负责可信业务事实；OpenAPI、权限与数据契约让三者持续对齐。
</div>

## 为什么会有这个项目

时间来到 2026 年，作者在一次次开发 App 项目时仍然遇到同一个问题：移动端框架很多，Admin 脚手架也很多，服务端模板同样不少，但当一个项目需要同时覆盖 App、运营后台、认证会话、多租户、国际化，尤其还要认真面对 HarmonyOS 时，开发者往往只能自己把几套彼此陌生的系统接在一起。

真正消耗人的，常常不是第一张业务页面，而是那些每个项目都必须做、却很难一次做对的基础工作：Token 应该存在哪里，Admin 和 Mobile 的身份如何隔离，权限怎样落到 SQL，双语如何贯穿 API 和界面，组件怎样在多个平台保持边界，接口变化又如何避免三端漂移。

AppKernia 就从这个遗憾出发。它不试图替开发者决定业务，而是希望把重复、脆弱又重要的地基一起做好。这样，一个独立开发者或小团队也能把更多时间留给真正有价值的产品，而不是把第一个月都花在重新搭建脚手架上。

## 名字的意义

`AppKernia` 的命名叙事由三部分组成：

<div className="ak-name-grid">
  <div>
    <strong>App</strong>
    <span>从用户手中的应用出发，关注真实的安装、会话、通知与跨平台体验。</span>
  </div>
  <div>
    <strong>Kern</strong>
    <span>表达“内核”与“核心”：认证、契约、权限、数据和工程质量应成为可复用的稳定底座。</span>
  </div>
  <div>
    <strong>-ia</strong>
    <span>代表一个可以生长的空间：不同业务在共同核心之上形成自己的产品与生态。</span>
  </div>
  <div>
    <strong>AK</strong>
    <span>简短的工程代号，贯穿 `ak-api`、`ak-admin`、`ak-mobile` 与 `ak-*` UI 组件。</span>
  </div>
</div>

这是一种项目自身的品牌解释：AppKernia 不是要成为一个把所有业务锁死的“大而全平台”，而是要做一颗可信、开放、可以被继续扩展的应用内核。

## 为什么选择这套技术

技术选择服务于边界和长期维护，而不是追逐一张热门技术清单。

| 产品面      | 核心选择                                             | 选择原因                                                                                                         |
| ----------- | ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Mobile      | uni-app x、UTS/UVue、VDOM、AK UI                     | 以同一业务层面向 Android、iOS 与 HarmonyOS，同时把平台差异关进 Port 与 Adapter；是否可用仍以各平台真实证据为准。 |
| Admin       | React、TypeScript strict、Vite、TanStack、Ant Design | 适合类型安全的运营 SPA、复杂表单和可测试的数据工作流；静态路由与动态菜单分开，避免运行时执行未知代码。           |
| Server      | GoFrame、pgx/v5、sqlc、PostgreSQL 18                 | 保留 Go 的显式边界与 PostgreSQL 的事务/约束能力，不用 ORM 隐藏租户过滤、锁和关键 SQL。                           |
| Contract    | OpenAPI 3.1、生成客户端、双语契约                    | 让接口字段、错误码、Audience 与语言规则成为三端共同事实，而不是靠口头约定。                                      |
| Async & ops | River、Transactional Outbox、OpenTelemetry           | 内部任务与外部事件职责分开，并从一开始保留可观测性、重试和审计边界。                                             |

如果你想先理解这些部分如何连接，请继续阅读[总体架构](../concepts/architecture)；如果你只想把项目跑起来，可以直接进入[从源码开始](./quick-start)。

## 现在与未来

AppKernia 仍处于走向首个稳定 Core 版本的阶段。当前重点不是堆叠更多页面，而是让认证、用户、租户、权限、文件、通知、内容、配置和移动端基础体验在代码、OpenAPI、数据库、双语与测试之间真正闭环。

接下来会沿着三条主线推进：

1. **把核心做稳**：完成关键安全与并发路径、版本化迁移、生成客户端和可重复的本地/CI 验收。
2. **把平台做实**：持续补齐 Android、iOS、HarmonyOS 的构建与真实设备证据，不用“理论支持”替代运行结果。
3. **让生态可参与**：提供更完整的示例业务、组件画廊、模块生成器、扩展 Port 与贡献者友好的任务入口。

路线图表达方向而不是承诺日期。每项能力是否完成，以仓库中的实现状态、测试和对应平台证据为准。你可以查看[路线图](./roadmap)和[项目实施状态](https://github.com/Payhon/AppKernia/blob/main/docs/IMPLEMENTATION_STATUS.md)。

## 从这里加入

你不需要先成为整个栈的专家：修正一句文档、补一个失败用例、复现一个平台问题、完善一个 `ak-*` 组件，都是有价值的贡献。

- 想先体验：按[快速开始](./quick-start)完成第一次本地运行。
- 想理解边界：阅读[核心概念](../concepts/)与[服务端 API](../api/)。
- 想提交改动：从[贡献指南](../community/contributing)选择适合自己的贡献阶梯。
- 如果这个方向也解决了你的痛点，欢迎在 [GitHub 为 AppKernia 点亮 Star](https://github.com/Payhon/AppKernia)，让更多开发者更早看到它。
